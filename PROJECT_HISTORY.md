# AiWebCity — история проекта и контекст для продолжения разработки

Дата фиксации: 2 сентября 2026

## 1. Идея проекта

AiWebCity — городской сервис для Новороссийска.

Главный сценарий:

1. Пользователь фотографирует объект на улице.
2. Загружает фотографию в сервис.
3. Указывает адрес или улицу (подсказка, а не обязательная истина).
4. Система должна определить, что именно попало на фото.
5. Если на фото конкретное здание — найти современные фотографии именно этого здания и подтвердить визуальное совпадение.
6. Если на фото улица/панорама/несколько зданий — система должна определить наиболее вероятный объект или несколько кандидатов, а не пытаться сделать вид, что на фото одно конкретное здание.
7. После подтверждения объекта система ищет реальные исторические фотографии этого места/здания по адресу, улице и координатам.
8. Только после качественной идентификации объекта планируется добавить AI-реконструкцию того, как место выглядело раньше.

Ключевой принцип: сначала достоверная идентификация и реальные источники, потом генерация.

## 2. Что НЕ является целью

Не нужно делать бесполезное «описание здания» вроде:

- «семиэтажное здание»;
- «светлый фасад»;
- «есть окна и балконы».

Vision нужен не для красивого описания. Он должен выполнять визуальную проверку: действительно ли две фотографии показывают один и тот же конкретный объект.

Также адрес, который ввёл пользователь, является подсказкой/ограничением поиска, но не должен автоматически считаться доказательством.

## 3. Жёсткое географическое ограничение

Проект работает ТОЛЬКО по Новороссийску.

Не расширять поиск на Краснодар, Геленджик и другие города без отдельного решения.

Поиск кандидатов и исторических источников должен максимально использовать Новороссийск как geographic scope.

## 5. Reverse image search

Изначально использовался PicImageSearch 3.12.11.

Проблема установки на Python 3.14:

PicImageSearch объявляет lxml < 6, но старый lxml 5.4.0 пытался собираться из исходников и падал при компиляции.

Рабочий workaround на сервере:

    pip install "lxml==6.0.3"
    pip install --no-deps "PicImageSearch==3.12.11"
    pip install "pyquery>=2.0.1" "cssselect>=1.5.0" "httpx[http2]>=0.28.1"

После этого:

    python -c "from PicImageSearch import Network, Yandex, GoogleLens; print('PicImageSearch OK')"

выдаёт:

    PicImageSearch OK

requirements.txt сейчас содержит lxml==6.0.3 и комментарий про отдельную установку PicImageSearch.

## 6. Что было не так с первым reverse search

Yandex возвращал много результатов, но:

- было много дублей;
- качество понимания конкретного здания было слабым;
- результаты могли относиться просто к району/городу;
- одинаковые изображения могли приходить несколько раз;
- заголовки и описания поисковика часто вводили в заблуждение.

Google Lens в тестах часто возвращал 0 результатов.

Позже был добавлен механизм получения полноразмерных Yandex Images, потому что thumbnails были слишком низкого качества для нормального visual comparison.

Файл:

    app/yandex_fullsize.py

## 7. Важное наблюдение про качество изображений

Ранее Yandex-кандидаты приходили в плохом thumbnail-разрешении. Это ухудшало визуальную проверку.

После добавления app/yandex_fullsize.py качество изображений стало значительно лучше.

Это направление нужно сохранять.

## 8. Текущий visual verification

Файл:

    app/visual_compare.py

Он отправляет в Timeweb Vision две картинки:

- IMAGE A — исходная фотография пользователя;
- IMAGE B — найденный кандидат.

Модель должна ответить JSON:

    {
      "same_place": true/false,
      "confidence": 0.0,
      "matching_features": [...],
      "contradictions": [...],
      "reason": "..."
    }

В prompt специально запрещено использовать:

- название сайта;
- URL;
- подпись;
- адрес;
- текст вокруг изображения

как визуальное доказательство.

Сравниваться должны:

- геометрия;
- характерные выступы;
- углы;
- расположение окон;
- балконы;
- колонны;
- входы;
- этажи;
- крыша;
- вывески;
- соседние объекты;
- другие уникальные детали.

Разный ракурс/сезон/цвет/транспорт не должны автоматически означать несовпадение.

При недостатке доказательств модель должна говорить «не подтверждено».

## 9. Почему visual comparison всё ещё недостаточно хорош

Главная текущая проблема проекта:

Система уже может довольно хорошо понять адрес/район, но часто не находит достаточное количество хороших фотографий именно того здания.

Особенно плохо работает сценарий, когда пользователь фотографирует НЕ конкретный фасад, а улицу.

Например, на фото может быть:

- несколько домов;
- дорога;
- часть перекрёстка;
- несколько фасадов;
- двор/пространство между зданиями.

В таком случае нельзя просто отправить одно исходное фото в reverse search и ожидать один точный результат.

Нужно переходить к multi-stage identification.

## 10. Желаемый алгоритм идентификации

Именно эту архитектуру считать целевой:

### Stage A — анализ исходного фото

Vision должен определить не «описание здания», а структуру сцены:

- есть ли один дом;
- есть ли несколько зданий;
- есть ли главный объект;
- какие части кадра являются зданиями;
- какие уникальные признаки пригодны для поиска;
- есть ли номер дома, вывеска, улица и т.п.

Если это улица, система должна уметь работать с несколькими потенциальными объектами.

### Stage B — получение большого пула кандидатов

Не ограничиваться несколькими случайными reverse-search результатами.

Нужно собирать кандидатов из:

- Yandex Images;
- Google Lens, если доступен;
- Wikimedia;
- PastVu;
- других легальных открытых источников, если они реально улучшают recall.

Важно: сначала recall, потом precision.

### Stage C — дедупликация

Удалять:

- одинаковые URL;
- одинаковые Yandex image IDs;
- один и тот же файл;
- почти одинаковые thumbnails;
- одну и ту же фотографию, размещённую на разных страницах.

20 результатов поисковика не должны превращаться в 20 карточек одного и того же изображения.

### Stage D — нормализация изображений

Для visual comparison нужны максимально качественные оригиналы/large images, а не маленькие thumbnails.

Нужно:

1. получить оригинальную/крупную картинку;
2. скачать её;
3. проверить HTTP status и content-type;
4. при необходимости привести к JPEG/PNG;
5. ограничить размер;
6. не отдавать Vision модельке мусорные/битые изображения.

### Stage E — визуальный reranking

Лучшие кандидаты нужно сравнивать с исходным фото.

Идея:

- сначала дешёвый/быстрый визуальный фильтр;
- затем Timeweb Vision для top-N;
- результаты сортируются по visual confidence.

При сравнении нельзя принимать решение только по совпадению текста.

### Stage F — cross-check адреса

Только после визуального кандидата нужно проверять адрес:

- адрес из результата;
- адрес пользователя;
- Новороссийск;
- координаты;
- улица;
- дом.

Если визуально совпадает, но адрес противоречит — кандидат должен быть отброшен или получить очень низкий рейтинг.

Если адрес совпадает, но визуально здание не совпадает — тоже нельзя считать его найденным.

Формула должна быть примерно:

    final_confidence =
        visual_match
        + address_match
        + geographic_match
        + source_quality

но с ограничением: сильное текстовое совпадение не должно компенсировать отсутствие визуального совпадения.

## 11. Особый сценарий: фотография улицы

Это один из самых важных сценариев.

Если фото содержит улицу:

1. определить несколько фасадов/объектов;
2. для каждого объекта получить crop;
3. искать каждый crop отдельно;
4. объединить кандидатов;
5. визуально сравнить;
6. понять, какой дом присутствует в исходном кадре;
7. только затем искать историю.

То есть:

    street photo
        ↓
    object/region detection
        ↓
    multiple crops
        ↓
    reverse search per crop
        ↓
    candidate pool
        ↓
    deduplication
        ↓
    visual verification
        ↓
    address/geography verification
        ↓
    confirmed building

Это намного перспективнее, чем пытаться распознать всю улицу одним запросом.

## 12. Исторические фотографии

После подтверждения здания:

### PastVu

Искать фотографии вокруг координат найденного объекта.

Использовать год/период, если пользователь его указал.

### Wikimedia Commons

Искать:

- адрес;
- улицу;
- название здания;
- Новороссийск;
- связанные поисковые запросы.

### PastPhoto

Использовать как дополнительный исторический источник.

Критическая логика не должна зависеть от хрупкого HTML scraping.

## 13. Что уже специально решили НЕ делать

Генерация исторического изображения пока выключена.

В health:

    generation: false

Сначала:

    найти → доказать → подтвердить адрес → найти исторические источники

И только потом:

    исторические фото → AI reconstruction

Не возвращаться к генерации, пока identification layer не станет надёжной.

# Часть 2. Переработка идентификации, 3 сентября 2026

## 23. Найденная причина плохого recall

Главная проблема из раздела 9 («система не находит достаточно фотографий именно
того здания») оказалась не проблемой ранкинга и не проблемой качества картинок.

PicImageSearch читает из ответа Яндекса ровно один блок:

    initialState.cbirSites.sites

Это «сайты, где встречается ЭТА ЖЕ САМАЯ картинка», то есть поиск точных копий
файла. Для фотографии, снятой пользователем на телефон и нигде не опубликованной,
этот блок пуст или почти пуст.

Замер на тестовом фото (ул. Советов, 34): Яндекс возвращал **3 результата**, и все
четыре варианта кропа давали одни и те же 3 результата. Google Lens стабильно
возвращал 0.

То есть сервис в принципе не умел находить другие фотографии того же здания —
только копии самой загруженной фотографии.

## 24. Что лежало в том же ответе и не использовалось

В том же самом HTTP-ответе, который код уже получал, находились:

| блок | содержимое | пример |
|---|---|---|
| `cbirSimilar.thumbs` | до 40 визуально похожих изображений | 40 из 40 на каждом тестовом фото |
| `cbirTags.tags` | текстовые догадки Яндекса | `губернского 1 новороссийск` |
| `cbirPreview.crops` | bbox детектора объектов | `('здание', 0.0, 0.24, 1.0, 0.88)` |
| `cbirOcr.plainText` | текст, распознанный на фото | вывески, номера домов |
| `cbirPreview.cbirId` | идентификатор запроса у Яндекса | |

`cbirSimilar` содержит `linkUrl`, внутри которого параметр `img_url` — это ссылка
на полноразмерный оригинал. Около 90 % похожих изображений отдают такой оригинал.

Детектор объектов Яндекса закрывает Stage A и Stage B целевого пайплайна из
раздела 10 бесплатно, в рамках уже выполняемого запроса.

## 25. Что сделано

Новый модуль `app/yandex_cbir.py` — собственный клиент Yandex CBIR. Делает один
POST и разбирает все пять блоков. PicImageSearch остался только ради Google Lens
и импортируется лениво.

`app/reverse_search.py` переписан:

- проход 1 — полный кадр;
- проходы 2–3 — кроп по bbox категории «здание» от детектора Яндекса;
- если здания детектор не нашёл, кадр режется своими правилами (сценарий улицы);
- кандидаты из `sites` и `similar` объединяются, дедуплицируются по yandex image id;
- текстовый ранкинг под Новороссийск определяет только ПОРЯДОК визуальной проверки;
- кэш по хэшу фото, пауза между запросами, отдельная детекция капчи.

Число запросов к Яндексу на фото ограничено `YANDEX_MAX_PASSES` (по умолчанию 3).

Новый модуль `app/image_fetch.py` — Stage D. Картинка кандидата скачивается на
нашей стороне с браузерными заголовками, проверяется по content-type, декодируется
через `draft()` и ужимается в JPEG. Раньше URL уходил в Vision как есть, и
недоступные источники молча превращались в «не совпадает».

`app/visual_compare.py`: сравнения идут параллельно (было последовательно, 12 подряд),
исходное фото ужимается один раз до 1024 px, кандидат — до 768 px, картинка
скачивается прямо перед сравнением и сразу отпускается.

Новый модуль `app/address_resolve.py` — Stage F. Адресные гипотезы собираются из
подписей ВИЗУАЛЬНО ПОДТВЕРЖДЁННЫХ кандидатов (основной вес), подсказок `cbirTags`,
OCR с фотографии и подсказки пользователя (минимальный вес), затем проверяются
через Nominatim с ограничением по bbox Новороссийска и паузой 1.1 с между запросами.

## 26. Два бага, из-за которых исторический слой не работал вообще

1. `pastvu_search` читал `result["photo"]`, а API отдаёт `result["photos"]`.
   PastVu ВСЕГДА возвращал пустой список. После исправления — 22–30 фотографий
   на каждую подтверждённую точку.
2. Wikimedia Commons отвечал `403 Please respect our robot policy` на
   User-Agent `AiWebCity/0.9`. Нужен UA с названием проекта и контактной ссылкой.
   Дополнительно `canonicalurl` приходит только при `prop=info&inprop=url`.

## 23. Замер от 3 сентября 2026

Тестовый набор: 7 фотографий зданий Новороссийска с известными адресами
(Wikimedia Commons: Советов 34/36/38/40, Губернского 1/2, Свободы 23) плюс один
негативный контроль — фотография сосны на улице Советов.

Каждое фото искажено перед подачей (кроп, поворот 1.8°, сжатие до 62%, JPEG q78),
чтобы точного совпадения файла в индексе не было и сценарий был похож на съёмку
с телефона.

| | было | стало |
|---|---|---|
| кандидатов на фото | 3 | 50–99 |
| адрес определён верно | — | 7 из 7 |
| ошибочно выданных адресов | — | 0 |
| исторических фотографий | 0 | 24 |
| vision-вызовов на фото | 14 | 6 |

Негативный контроль (сосна) получил статус `visual_only` без адреса — сервис не
выдумал здание.

### Что оказалось главной причиной плохого recall

PicImageSearch читает из ответа Яндекса только `initialState.cbirSites.sites` —
блок «сайты, где встречается ЭТА ЖЕ картинка». Для фотографии, которой нет в
интернете, он почти пуст. В том же самом HTTP-ответе лежало неиспользованным:

    cbirSimilar.thumbs   до 40 визуально похожих изображений
    cbirTags.tags        текстовые догадки Яндекса, часто прямо адрес
    cbirPreview.crops    bbox объектов от детектора («здание», «машина»)
    cbirOcr.plainText    текст, распознанный на фотографии

Отсюда `app/yandex_cbir.py` — собственный разбор ответа вместо парсера библиотеки.

### Найденные по дороге баги

* `pastvu_search` читал ключ `result.photo`, а API отдаёт `result.photos` —
  исторические фотографии не находились никогда.
* Wikimedia Commons отвечает 403 на User-Agent без названия проекта и контакта,
  плюс `canonicalurl` требует `prop=info&inprop=url`.
* Шаблон улицы требовал пробел после «ул.», из-за чего подпись «Ул.Губернского 2»
  не давала адреса вообще.
* Кандидаты уходили в Vision ссылкой, и часть источников отдавала 403 — теперь
  картинка скачивается и нормализуется на нашей стороне.

### Правило подтверждения адреса

Подписи кандидатов берутся со страниц, которые мы не проверяли, поэтому их
согласие между собой доказательством не является. На `ул. Советов, 38` все
подтверждённые кандидаты дружно вели на другой корпус того же колледжа на
ул. Рубина, 5 — в 1958 м. Теперь адрес засчитывается, только если улицу называет
источник, полученный из самой фотографии: `cbirTags`, OCR или подсказка
пользователя. Иначе статус `visual_only`, адрес отдаётся как `address_guess`, и
исторические фотографии не запрашиваются.

### Ограничения окружения

* VPS 889 МБ RAM. Первая версия ловила OOM-killer: скачанные картинки держались
  в памяти все сразу. Сейчас кандидат скачивается перед сравнением и сразу
  отпускается, JPEG декодируется через `draft()`.
* Тариф Timeweb AI — главный расходный лимит: за сессию разработки он кончался
  дважды, примерно после 210 vision-вызовов.

## 24. Проверка на случайном здании (ул. Куникова, 43)

Владелец проверил сервис на произвольном здании — котельная «Атэк», ул. Куникова, 43 —
загрузив скриншот Яндекс-панорамы и **введя адрес в подсказку**.

Визуальный поиск отработал: пять подтверждённых фотографий, все того же здания с
характерной красно-белой трубой. Адрес при этом не определился.

Причина: поле «адрес-подсказка» разбиралось теми же шаблонами, что и случайный
текст со страницы, а они требуют либо слово «ул.», либо название города. Введённое
«куникова 43» не подходило ни под один шаблон и **отбрасывалось целиком**. То есть
единственный источник, который мог подтвердить улицу, молча терялся.

Теперь поле подсказки разбирается отдельным мягким шаблоном: оно заведомо содержит
адрес, поэтому ни «ул.», ни город не обязательны.

Важно, что подсказка по-прежнему не подтверждает сама себя: улица считается
подтверждённой, только если её назвал ещё какой-то источник. Если пользователь ввёл
адрес, а ни один кандидат и ни одна подсказка Яндекса его не упоминают, статус
остаётся `visual_only`, а адрес показывается как предположение.

### Про нестабильность подсказок Яндекса

`cbirTags` меняются от запуска к запуску. На ул. Советов, 38 один прогон дал
подтверждённый верный адрес, следующий — `visual_only` с предположением
«переулок Рубина, 5». Поведение корректное (без подтверждения адрес не выдаётся),
но означает, что результат по одному и тому же фото может отличаться. Это аргумент
за то, чтобы просить пользователя вводить адрес-подсказку.

## 25. Проверка адреса встречным поиском

Повторная проверка на ул. Куникова, 43 показала, что мягкого разбора подсказки
мало. Подсказка чинит разбор, но улица всё равно должна быть названа кем-то ещё,
а среди найденных фотографий котельной подписей с адресом не оказалось вовсе —
при том что сами фотографии были правильные.

Проблема в самой природе доказательства: подпись страницы — это текст с сайта,
который мы не проверяли. Если подписи нет, доказывать нечем.

`app/address_probe.py` заходит с другой стороны. Берём адрес-гипотезу (сначала
подсказку пользователя, затем лучшие гипотезы), ищем в Яндексе фотографии ПО
ЭТОМУ АДРЕСУ и визуально сравниваем их с фотографией пользователя. Совпало —
адрес доказан изображением. Не совпало — гипотеза отбрасывается, как бы дружно
её ни называли подписи.

Текстовый поиск по адресу отдаёт панорамы Яндекса, снятые прямо у этого дома, —
это идеальный эталон: здание целиком, снято с улицы.

Проверено на фотографии котельной «Атэк»:

    куникова 43  -> 3 совпадения из 3 (уверенность 1.00, 0.90, 0.90)
    советов 34   -> 0 совпадений из 3

То есть проба и подтверждает верный адрес, и отклоняет неверный.

Проба включается только тогда, когда адрес не подтвердился обычным путём, и
ограничена `ADDRESS_PROBE_LIMIT` адресами по `ADDRESS_PROBE_IMAGES` фотографий,
чтобы не разгонять расход Vision.

### Почему база адресов Новороссийска это не решает

Отдельно рассматривался вариант загрузить базу адресов города. Он не помогает:
вопрос не в том, существует ли Куникова 43 — это и так проверяется через
OpenStreetMap, — а в том, стоит ли сфотографированное здание именно там. На это
отвечает только сравнение изображений. База адресов пригодится позже, для
офлайн-геокодирования без лимитов Nominatim.
