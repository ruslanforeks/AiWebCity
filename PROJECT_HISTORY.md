# AiWebCity — история проекта и контекст для продолжения разработки

Дата фиксации: 2 сентября 2026

## 1. Идея проекта

AiWebCity — городской сервис для Новороссийска.

Главный сценарий:

1. Пользователь фотографирует объект на улице.
2. Загружает фотографию в сервис.
3. Указывает адрес или улицу (подсказка, а не обязательная истина).
4. Система должна определить, что именно попало на фото.
5. Если на фото конкретное здание — найти современные фотографии именно этого здания и подтвердить визуальное совпадение.
6. Если на фото улица/панорама/несколько зданий — система должна определить наиболее вероятный объект или несколько кандидатов, а не пытаться сделать вид, что на фото одно конкретное здание.
7. После подтверждения объекта система ищет реальные исторические фотографии этого места/здания по адресу, улице и координатам.
8. Только после качественной идентификации объекта планируется добавить AI-реконструкцию того, как место выглядело раньше.

Ключевой принцип: сначала достоверная идентификация и реальные источники, потом генерация.

## 2. Что НЕ является целью

Не нужно делать бесполезное «описание здания» вроде:

- «семиэтажное здание»;
- «светлый фасад»;
- «есть окна и балконы».

Vision нужен не для красивого описания. Он должен выполнять визуальную проверку: действительно ли две фотографии показывают один и тот же конкретный объект.

Также адрес, который ввёл пользователь, является подсказкой/ограничением поиска, но не должен автоматически считаться доказательством.

## 3. Жёсткое географическое ограничение

Проект работает ТОЛЬКО по Новороссийску.

Не расширять поиск на Краснодар, Геленджик и другие города без отдельного решения.

Поиск кандидатов и исторических источников должен максимально использовать Новороссийск как geographic scope.

## 5. Reverse image search

Изначально использовался PicImageSearch 3.12.11.

Проблема установки на Python 3.14:

PicImageSearch объявляет lxml < 6, но старый lxml 5.4.0 пытался собираться из исходников и падал при компиляции.

Рабочий workaround на сервере:

    pip install "lxml==6.0.3"
    pip install --no-deps "PicImageSearch==3.12.11"
    pip install "pyquery>=2.0.1" "cssselect>=1.5.0" "httpx[http2]>=0.28.1"

После этого:

    python -c "from PicImageSearch import Network, Yandex, GoogleLens; print('PicImageSearch OK')"

выдаёт:

    PicImageSearch OK

requirements.txt сейчас содержит lxml==6.0.3 и комментарий про отдельную установку PicImageSearch.

## 6. Что было не так с первым reverse search

Yandex возвращал много результатов, но:

- было много дублей;
- качество понимания конкретного здания было слабым;
- результаты могли относиться просто к району/городу;
- одинаковые изображения могли приходить несколько раз;
- заголовки и описания поисковика часто вводили в заблуждение.

Google Lens в тестах часто возвращал 0 результатов.

Позже был добавлен механизм получения полноразмерных Yandex Images, потому что thumbnails были слишком низкого качества для нормального visual comparison.

Файл:

    app/yandex_fullsize.py

## 7. Важное наблюдение про качество изображений

Ранее Yandex-кандидаты приходили в плохом thumbnail-разрешении. Это ухудшало визуальную проверку.

После добавления app/yandex_fullsize.py качество изображений стало значительно лучше.

Это направление нужно сохранять.

## 8. Текущий visual verification

Файл:

    app/visual_compare.py

Он отправляет в Timeweb Vision две картинки:

- IMAGE A — исходная фотография пользователя;
- IMAGE B — найденный кандидат.

Модель должна ответить JSON:

    {
      "same_place": true/false,
      "confidence": 0.0,
      "matching_features": [...],
      "contradictions": [...],
      "reason": "..."
    }

В prompt специально запрещено использовать:

- название сайта;
- URL;
- подпись;
- адрес;
- текст вокруг изображения

как визуальное доказательство.

Сравниваться должны:

- геометрия;
- характерные выступы;
- углы;
- расположение окон;
- балконы;
- колонны;
- входы;
- этажи;
- крыша;
- вывески;
- соседние объекты;
- другие уникальные детали.

Разный ракурс/сезон/цвет/транспорт не должны автоматически означать несовпадение.

При недостатке доказательств модель должна говорить «не подтверждено».

## 9. Почему visual comparison всё ещё недостаточно хорош

Главная текущая проблема проекта:

Система уже может довольно хорошо понять адрес/район, но часто не находит достаточное количество хороших фотографий именно того здания.

Особенно плохо работает сценарий, когда пользователь фотографирует НЕ конкретный фасад, а улицу.

Например, на фото может быть:

- несколько домов;
- дорога;
- часть перекрёстка;
- несколько фасадов;
- двор/пространство между зданиями.

В таком случае нельзя просто отправить одно исходное фото в reverse search и ожидать один точный результат.

Нужно переходить к multi-stage identification.

## 10. Желаемый алгоритм идентификации

Именно эту архитектуру считать целевой:

### Stage A — анализ исходного фото

Vision должен определить не «описание здания», а структуру сцены:

- есть ли один дом;
- есть ли несколько зданий;
- есть ли главный объект;
- какие части кадра являются зданиями;
- какие уникальные признаки пригодны для поиска;
- есть ли номер дома, вывеска, улица и т.п.

Если это улица, система должна уметь работать с несколькими потенциальными объектами.

### Stage B — получение большого пула кандидатов

Не ограничиваться несколькими случайными reverse-search результатами.

Нужно собирать кандидатов из:

- Yandex Images;
- Google Lens, если доступен;
- Wikimedia;
- PastVu;
- других легальных открытых источников, если они реально улучшают recall.

Важно: сначала recall, потом precision.

### Stage C — дедупликация

Удалять:

- одинаковые URL;
- одинаковые Yandex image IDs;
- один и тот же файл;
- почти одинаковые thumbnails;
- одну и ту же фотографию, размещённую на разных страницах.

20 результатов поисковика не должны превращаться в 20 карточек одного и того же изображения.

### Stage D — нормализация изображений

Для visual comparison нужны максимально качественные оригиналы/large images, а не маленькие thumbnails.

Нужно:

1. получить оригинальную/крупную картинку;
2. скачать её;
3. проверить HTTP status и content-type;
4. при необходимости привести к JPEG/PNG;
5. ограничить размер;
6. не отдавать Vision модельке мусорные/битые изображения.

### Stage E — визуальный reranking

Лучшие кандидаты нужно сравнивать с исходным фото.

Идея:

- сначала дешёвый/быстрый визуальный фильтр;
- затем Timeweb Vision для top-N;
- результаты сортируются по visual confidence.

При сравнении нельзя принимать решение только по совпадению текста.

### Stage F — cross-check адреса

Только после визуального кандидата нужно проверять адрес:

- адрес из результата;
- адрес пользователя;
- Новороссийск;
- координаты;
- улица;
- дом.

Если визуально совпадает, но адрес противоречит — кандидат должен быть отброшен или получить очень низкий рейтинг.

Если адрес совпадает, но визуально здание не совпадает — тоже нельзя считать его найденным.

Формула должна быть примерно:

    final_confidence =
        visual_match
        + address_match
        + geographic_match
        + source_quality

но с ограничением: сильное текстовое совпадение не должно компенсировать отсутствие визуального совпадения.

## 11. Особый сценарий: фотография улицы

Это один из самых важных сценариев.

Если фото содержит улицу:

1. определить несколько фасадов/объектов;
2. для каждого объекта получить crop;
3. искать каждый crop отдельно;
4. объединить кандидатов;
5. визуально сравнить;
6. понять, какой дом присутствует в исходном кадре;
7. только затем искать историю.

То есть:

    street photo
        ↓
    object/region detection
        ↓
    multiple crops
        ↓
    reverse search per crop
        ↓
    candidate pool
        ↓
    deduplication
        ↓
    visual verification
        ↓
    address/geography verification
        ↓
    confirmed building

Это намного перспективнее, чем пытаться распознать всю улицу одним запросом.

## 12. Исторические фотографии

После подтверждения здания:

### PastVu

Искать фотографии вокруг координат найденного объекта.

Использовать год/период, если пользователь его указал.

### Wikimedia Commons

Искать:

- адрес;
- улицу;
- название здания;
- Новороссийск;
- связанные поисковые запросы.

### PastPhoto

Использовать как дополнительный исторический источник.

Критическая логика не должна зависеть от хрупкого HTML scraping.

## 13. Что уже специально решили НЕ делать

Генерация исторического изображения пока выключена.

В health:

    generation: false

Сначала:

    найти → доказать → подтвердить адрес → найти исторические источники

И только потом:

    исторические фото → AI reconstruction

Не возвращаться к генерации, пока identification layer не станет надёжной.

## 14. UI

В результате reverse search раньше показывались:

- изображение;
- заголовок;
- описание;
- «Открыть источник».

Это решили убрать.

Нужный пользовательский интерфейс должен быть значительно чище:

- сама фотография;
- степень совпадения;
- статус подтверждения;
- при необходимости адрес/объект;
- исторические фотографии.

Не нужно перегружать пользователя SEO-заголовками поисковика и длинными описаниями.

## 15. История экспериментов

### Эксперимент 1

Использовали reverse image search.

Yandex находил реальные картинки Новороссийска, но качество и релевантность были слабые.

Google Lens часто давал 0 результатов.

### Эксперимент 2

Добавили Vision.

Проблема: модель могла описывать объект, но это не решало идентификацию.

Вывод:

Vision должен использоваться для сравнения конкретных изображений, а не для бесполезного описания «7 этажей и окна».

### Эксперимент 3

Добавили visual_compare.py.

Это позволило проверять:

    исходное фото ↔ найденная фотография

по визуальным признакам.

### Эксперимент 4

Заметили, что Yandex отдаёт маленькие изображения.

Добавили:

    app/yandex_fullsize.py

После этого качество кандидатов заметно выросло.

### Текущий статус

Качество изображений стало гораздо лучше, но recall/поиск именно нужного здания всё ещё недостаточный.

Это текущая главная техническая задача.

## 18. Приватность

AiWebCity не должен сохранять исходное фото пользователя на VPS.

Фото может находиться в памяти процесса на время обработки.

При reverse image search фотография передаётся внешним поисковым сервисам. Это нужно учитывать в архитектуре и пользовательском уведомлении.

## 19. Что делать дальше

Приоритет №1:

Улучшить recall поиска конкретного здания.

Не пытаться сразу улучшать генерацию.

Приоритет №2:

Поддержать street photos через выделение нескольких регионов/зданий.

Приоритет №3:

Улучшить candidate retrieval:

- больше источников;
- большие изображения;
- дедупликация;
- несколько запросов;
- crop-based search.

Приоритет №4:

Улучшить visual verification:

- сравнивать top-N;
- использовать несколько crops;
- учитывать ракурс;
- не доверять текстовым метаданным;
- возвращать confidence и matching/contradicting features.

Приоритет №5:

После подтверждения объекта улучшить поиск исторических фотографий.

Приоритет №6:

Только после этого реализовывать AI-реконструкцию.

Ожидаемая последовательность:

    cd ~/AiWebCity

    source .venv/bin/activate

    lxml 6.0.3

и что PicImageSearch импортируется:

    python -c "from PicImageSearch import Network, Yandex, GoogleLens; print('PicImageSearch OK')"

    nohup uvicorn app.main_pic:app \

## 22. Контекст для следующего AI-разработчика

Если этот файл читается Claude/другим AI, не начинай проект с нуля.

Сначала:

1. прочитай README.md;
2. прочитай этот файл;
3. прочитай app/main_pic.py;
4. прочитай app/reverse_search.py;
5. прочитай app/yandex_fullsize.py;
6. прочитай app/visual_compare.py;
7. прочитай static/index_pic.html;
8. пойми текущий API flow;
9. только после этого меняй код.

Главная задача сейчас:

**Не описание здания. Не генерация. Не дизайн.**

**Нужно научить систему находить достаточно качественных фотографий именно того здания/объекта, который находится на фотографии пользователя, в том числе когда пользователь фотографирует целую улицу.**

После получения кандидатов система должна доказать визуальное совпадение и только потом использовать адрес/географию для подтверждения.

Целевой pipeline:

    USER PHOTO
        ↓
    SCENE / OBJECT ANALYSIS
        ↓
    BUILDING CROPS (если нужно)
        ↓
    MULTI-SOURCE SEARCH
        ↓
    FULL-SIZE IMAGE RETRIEVAL
        ↓
    DEDUPLICATION
        ↓
    VISUAL RERANKING
        ↓
    ADDRESS + GEO CROSS-CHECK
        ↓
    CONFIRMED BUILDING
        ↓
    HISTORICAL SEARCH
        ↓
    [позже] AI RECONSTRUCTION
